## 2. Organization Lifecycle Domain Model & State Machine

### 2.1 State Taxonomy

The organization lifecycle is modeled by `OrganizationLifecycleStatus` in `lib/types/organizations.ts`:

| Status | Code | Description | Semantic Meaning |
|---|---|---|---|
| **Draft** | `draft` | Organization created as unsubmitted draft | Preliminary registration, incomplete onboarding |
| **Pending** | `pending` | Submitted for platform administrator review | Ready for verification, awaiting activation |
| **Active** | `active` | Fully operational school tenant | Authorized for platform access and tenant login |
| **Suspended** | `suspended` | Temporarily blocked due to policy/payment/compliance | Tenant users blocked; administrative access preserved |
| **Inactive** | `inactive` | Voluntary hiatus or dormancy | Tenant idle; no billing active |
| **Archived** | `archived` | Decommissioned, preserved for regulatory retention | Read-only historical tenant; non-operational |

### 2.2 Transition Evaluation Engine (`lib/lifecycle/evaluator.ts`)

Transitions between lifecycle states are governed by an explicit state transition matrix:

```
                  ┌─────────┐
                  │  Draft  │
                  └────┬────┘
                       │ (submit_for_review)
                       ▼
                  ┌─────────┐
         ┌───────►│ Pending │◄──────────────┐
         │        └────┬────┘               │
         │             │ (approve_activate) │
         │             ▼                    │
         │        ┌─────────┐               │
         │        │ Active  │               │
         │        └────┬────┘               │
         │             │ (suspend)          │
         │             ▼                    │
         │        ┌─────────┐               │
         │ (reopen)│Suspended├───────────────┤ (reactivate)
         │        └────┬────┘               │
         │             │ (archive)          │
         │             ▼                    │
         │        ┌─────────┐               │
         │        │Archived │               │
         │        └─────────┘               │
         │             ▲                    │
         │             │ (archive)          │
         └─────────────┴────────────────────┘
```

#### Allowed Transition Rules

1. `draft` ➔ `pending`: Allowed upon submitting onboarding configuration.
2. `draft` ➔ `archived`: Allowed if abandoned prior to review (reason required).
3. `pending` ➔ `active`: Allowed upon Super-Admin verification and activation.
4. `pending` ➔ `draft`: Allowed if additional onboarding information is required.
5. `pending` ➔ `archived`: Allowed if registration is rejected.
6. `active` ➔ `suspended`: **Mandatory justification required** (minimum 5 characters) for non-payment, compliance audit, or terms violation.
7. `active` ➔ `inactive`: Allowed for seasonal or operational hiatus.
8. `active` ➔ `archived`: Allowed for formal tenant decommissioning (reason required).
9. `suspended` ➔ `active`: Allowed for reactivation upon compliance resolution.
10. `suspended` ➔ `archived`: Allowed for terminal decommission of suspended tenant.
11. `inactive` ➔ `active`: Allowed for reactivation from dormancy.
12. `inactive` ➔ `archived`: Allowed for archiving dormant tenant.
13. `archived` ➔ `draft`: Allowed under strict administrative override ("Reopen as draft").

#### Enforced Preconditions & Rejections
- **Mandatory Justification:** Any transition to `suspended` or `archived` without a valid explanation string (min 5 characters) is rejected with `reason_required` or `reason_too_short`.
- **Unsupported Transitions:** Illegal jumps (e.g., `draft` directly to `active` without review, or `archived` directly to `active`) are strictly blocked by `evaluateLifecycleTransition()` and surfaced to the UI with clear explanations.

## 3. Multi-Campus & Branch Governance Architecture

School organizations frequently operate multi-branch campuses, specialized athletic complexes, satellite early-learning centers, or regional campuses.

### 3.1 Campus Contract Schema (`lib/types/campuses.ts`)

```typescript
export interface Campus {
  id: string;                       // Unique campus identifier (e.g., 'cmp_001_1')
  organizationId: string;           // Foreign key referencing parent organization
  name: string;                     // Full campus name (e.g., 'Highland Main Campus')
  code: string;                     // Alphanumeric campus code (e.g., 'MAIN', 'NORTH')
  isMainCampus: boolean;            // Boolean main campus designation flag
  type: CampusType;                 // 'main' | 'branch' | 'satellite' | 'specialized'
  status: CampusStatus;             // 'active' | 'inactive' | 'planned' | 'under_maintenance'
  address: CampusAddress;           // Street, city, stateOrProvince, country, postalCode
  contactEmail?: string;            // Campus administrative email
  contactPhone?: string;            // Campus telephone
  principalName?: string;           // Head of campus / Principal
  studentCapacity?: number;         // Facility enrollment capacity limit
  createdAt: string;                // ISO timestamp
  updatedAt: string;                // ISO timestamp
}
```

### 3.2 Campus Governance Rules
1. **Strict Organization Ownership:** Every campus record must reference a valid existing organization ID. Unassigned or orphaned campuses are blocked at creation.
2. **Campus Code Uniqueness Scoped to Tenant:** Campus codes (e.g. `NORTH`, `MAIN`) must be unique *within the same organization*. Different organizations may independently use `MAIN` or `NORTH`.
3. **Single Main Campus Invariant:** Every organization with campuses must have exactly one designated main campus. Designating a new main campus via `setMainCampus(orgId, campusId)` automatically unsets `isMainCampus` on previously designated campuses.
4. **Main Campus Deletion Guard:** The designated main campus cannot be deleted if secondary campuses exist. Another campus must be promoted to main campus first.
5. **Plan Quota Guard:** Campus creation enforces plan limits (e.g. Starter tier: 1 campus; Growth tier: 3 campuses; Enterprise: unlimited).
6. **Dynamic Campus Counting:** Directory badges, overview cards, and filter counts are derived dynamically from `campuses.filter(c => c.organizationId === org.id)`.

### 3.3 Development Fixtures (`INITIAL_CAMPUSES`)
17 realistic, geographically coherent campuses were seeded across all 10 platform organizations in `lib/data/initial-data.ts`, ensuring immediate testability and realistic UI rendering.

## 4. Configuration Readiness Engine (`lib/readiness/evaluator.ts`)

Rather than relying on vague onboarding indicators, Phase E-09.7 implements an automated **8-Dimensional Configuration Readiness Evaluator**:

| Item ID | Check Category | Evaluated Conditions | Weight | Blocker Severity |
|---|---|---|---|---|
| `profile_identity` | Profile & Identity | Name, code, subdomain, classification defined | 15% | High Blocker |
| `admin_contact` | Contact & Admin | Primary contact email, phone, admin coordinates | 10% | Medium Attention |
| `campuses_registered` | Campus Topology | At least 1 campus registered with 1 designated main | 20% | High Blocker |
| `subscription_assigned` | Commercial Plan | Active subscription plan linked to organization | 15% | High Blocker |
| `module_entitlements` | Module Catalog | Effective entitlement catalog verified (>0 modules) | 15% | Medium Attention |
| `technical_regional` | Technical Settings | Timezone, locale, and date format configured | 10% | Low Attention |
| `domain_readiness` | Ingress & Routing | Subdomain string conforms to RFC 1035 format | 10% | High Blocker |
| `resource_allocation` | Resource Quota | Storage allocation limit specified (>0 GB) | 5% | Low Attention |

### Scoring & Status Derivation
- **Total Score:** Calculated as sum of passing item weights (0% to 100%).
- **Blocker Count:** Count of incomplete items flagged with `'blocker'`.
- **Readiness State:**
  - `ready` (100% score, 0 blockers)
  - `needs_attention` (>=70% score, 0 blockers)
  - `not_ready` (<70% score or >=1 blocker)

## 5. Simulated Tenant Provisioning Engine (`lib/provisioning/simulator.ts`)

### 5.1 Boundaries & Architecture
The provisioning engine visualizes tenant activation through a transparent 5-step local simulation pipeline:
1. `dns_routing`: Subdomain routing verification and DNS record reservation.
2. `db_container`: Dedicated multi-tenant schema isolation boundary initialization.
3. `campus_link`: Primary branch mapping and academic year baseline initialization.
4. `module_catalog`: Entitlement catalog synchronization and override application.
5. `admin_dispatch`: Initial administrative credentials and onboarding email dispatch.

### 5.2 Deterministic Execution & Negative Testing Controls
- **Prerequisite Enforcement:** Provisioning is blocked if readiness blockers exist (e.g. missing campuses or invalid subdomain).
- **Negative Testing Toggle:** Administrators can toggle `"Simulate failure during provisioning run"` to test error handling and recovery workflows.
- **Local Event Logging:** Every step records timestamped events in the demonstration ledger.
- **State Transition:** Updates the organization's `provisioningStatus` to `'simulated_complete'` or `'simulated_failed'`.
- **Audit Integration:** Records `SIMULATED_PROVISIONING_RUN` in `PlatformStore` audit logs.

## 9. Known Gaps & Unresolved Business Rules

1. **Academic Year & Term Inheritance Across Campuses:**
   - *Current State:* Campuses are managed as independent physical facilities with capacity and addresses.
   - *Gap:* The exact operational model for whether satellite campuses inherit central academic terms or maintain independent timetables belongs to tenant application SIS workflows.
2. **Automated Subdomain DNS Propagation:**
   - *Current State:* Subdomains are validated for RFC 1035 compliance and checked for collisions locally.
   - *Gap:* Live Cloudflare/AWS Route53 automated record propagation requires a secure backend agent.
3. **Cross-Campus User Staffing Constraints:**
   - *Current State:* Campuses record head-of-campus principal names as text metadata.
   - *Gap:* Multi-branch staff role assignments and roving teacher schedules require backend SIS permission trees.
4. **Subscription Quota Hard Enforcement vs. Soft Overdraft:**
   - *Current State:* UI warns when an organization exceeds its plan campus count.
   - *Gap:* Whether backend services should hard-block campus creation or trigger automatic prorated tier upgrades requires business policy definition.
