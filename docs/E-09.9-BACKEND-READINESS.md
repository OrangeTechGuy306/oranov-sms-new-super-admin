# PHASE E-09.9: BACKEND READINESS & CONTRACT SPECIFICATIONS
## Academics, Curriculum, Timetabling & Teaching Workflows

---

### Executive Confirmation

**NO BACKEND IMPLEMENTATION WAS INTRODUCED DURING PHASE E-09.9.**

All frontend components, metrics, evaluators, and views in `dashboard/` operate strictly against typed development adapters and deterministic mock fixtures. This document provides the engineering specifications, database schema recommendations, API endpoints, cross-tenant security guarantees, and performance requirements necessary for future backend implementation.

---

## 1. Required API Endpoints for Platform Academic Oversight

To support the Super-Admin academic oversight views implemented in Phase E-09.9, the future backend must expose the following authenticated platform-level endpoints:

```
GET /api/v1/superadmin/academic-oversight
GET /api/v1/superadmin/academic-oversight/summary
GET /api/v1/superadmin/academic-oversight/organizations/:organizationId
GET /api/v1/superadmin/academic-oversight/export
GET /api/v1/superadmin/academic-oversight/capabilities
```

### 1.1 Global Oversight Summary
- **Endpoint:** `GET /api/v1/superadmin/academic-oversight/summary`
- **RBAC Guard:** `superadmin.academics.view`
- **Query Parameters:**
  - `academicSession?: string`
  - `activePeriod?: string`
  - `readinessLevel?: string`
- **Response Schema:** Matches `AggregatedAcademicOversightMetrics` (total organizations, active periods, calendar integrity %, readiness index, timetable conflict counts, grading scale counts, reporting readiness %).

### 1.2 Tenant-Scoped Academic Configuration Query
- **Endpoint:** `GET /api/v1/superadmin/academic-oversight/organizations/:organizationId`
- **RBAC Guard:** `superadmin.academics.view`
- **Response Schema:** Matches `OrganizationAcademicOversight` (organization metadata, campuses, academic years, departments/classes/subjects, curriculum blueprints, timetable status and conflicts, pedagogical compliance, assessment config, data quality issues, and readiness checklist evaluation).

### 1.3 Aggregate CSV Export
- **Endpoint:** `GET /api/v1/superadmin/academic-oversight/export`
- **Format:** `text/csv` (RFC 4180 with formula injection neutralization)
- **Filters:** All standard filter parameters supported by the frontend.

## 2. Relational Schema & Persistence Requirements

Future backend implementations should establish or interface with the following relational structures:

### 2.1 Academic Sessions & Periods (`academic_sessions`, `academic_periods`)
```sql
CREATE TABLE academic_sessions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    name VARCHAR(50) NOT NULL, -- e.g. "2026/2027"
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PLANNED', -- PLANNED, ACTIVE, COMPLETED, ARCHIVED
    is_current BOOLEAN NOT NULL DEFAULT FALSE,
    description TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_session_dates CHECK (start_date < end_date)
);

CREATE TABLE academic_periods (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    session_id UUID NOT NULL REFERENCES academic_sessions(id) ON DELETE CASCADE,
    name VARCHAR(100) NOT NULL, -- e.g. "Autumn Term (Term 1)"
    type VARCHAR(20) NOT NULL DEFAULT 'TERM', -- TERM, SEMESTER, QUARTER, CUSTOM
    sequence INTEGER NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PLANNED',
    is_current BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    CONSTRAINT chk_period_dates CHECK (start_date < end_date)
);
```

### 2.2 Academic Structure & Faculty Assignments (`departments`, `classes`, `class_arms`, `subjects`, `teacher_assignments`)
- Enforce unique class codes per tenant campus.
- Enforce subject code uniqueness per tenant.
- Enforce non-overlapping primary teacher designations per class arm and subject.

### 2.3 Curriculum Blueprints & Schemes of Work (`curriculum_blueprints`, `schemes_of_work`)
- `curriculum_blueprints`: JSONB column for structured units, topics, learning objectives, and Bloom taxonomy mappings.
- `schemes_of_work`: State machine tracking status (`DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `APPROVED`, `RETURNED_FOR_REVISION`, `REJECTED`, `ARCHIVED`) with immutable revision snapshots.

### 2.4 Timetable & Conflict Engine (`timetables`, `timetable_slots`)
- Fast spatial/interval queries:
  ```sql
  -- Fast index to detect teacher double-booking
  CREATE INDEX idx_timetable_teacher_conflict 
  ON timetable_slots(tenant_id, teacher_id, day_of_week, start_time, end_time);

  -- Fast index to detect room clashing
  CREATE INDEX idx_timetable_room_conflict 
  ON timetable_slots(tenant_id, room_id, day_of_week, start_time, end_time);

  -- Fast index to detect class double-booking
  CREATE INDEX idx_timetable_class_conflict 
  ON timetable_slots(tenant_id, class_arm_id, day_of_week, start_time, end_time);
  ```

### 2.5 Assessment & Grading Scales (`grading_scales`, `grade_bands`)
- Scalable storage of letter grade, percentage, GPA 4.0, and competency scales.
- Pass mark threshold validation before report card publishing.

## 3. Server-Side Authorization & Multi-Tenant Isolation

### 3.1 Strict Row-Level Security (RLS)
- In the tenant-facing application, every query MUST be constrained by `tenant_id = current_setting('app.current_tenant_id')`.
- Super-Admin oversight queries operate via a dedicated read-only aggregation schema or database replica that:
  1. Aggregates counts and statuses grouped by `tenant_id`.
  2. Does not join with or project sensitive personal tables (e.g. `students`, `guardians`, `user_credentials`, `student_marks`).

### 3.2 Granular Platform RBAC Permissions
- `superadmin.academics.view`: Access the Academic Oversight workspace and view aggregated statistics.
- `superadmin.academics.export`: Generate aggregate CSV exports.
- **RESTRICTION:** Super-Admin users MUST NOT possess permissions to approve lesson plans, change grades, or alter tenant timetables remotely. Tenant autonomy must be preserved.

## 4. Audit Logging & Security Events

The backend must record structured audit events in `audit_logs` for any administrative oversight interactions:
- `ACADEMIC_OVERSIGHT_ACCESSED`: Logged with actor ID, timestamp, and active filter parameters.
- `ACADEMIC_OVERSIGHT_EXPORTED`: Logged when an administrator downloads aggregate CSV reports.
- `ACADEMIC_READINESS_ALERT_DISPATCHED`: Logged if an automated warning is sent to an organization with critical scheduling conflicts or missing grading scales.

## 5. Performance, Aggregation & Caching Strategy

1. **Pre-aggregated Rollups (Materialized Views):**
   - For high-volume multi-tenant environments, run an hourly background rollup job that compiles `organization_academic_summaries` materialized views.
   - Prevents live table scans across millions of timetable slots, daily plans, and student enrollments.

2. **Redis In-Memory Cache:**
   - Cache `superadmin:academic-oversight:summary` with a 5-minute TTL.
   - Invalidate on major lifecycle events (e.g., session activation, timetable publication).

3. **Query Latency SLA:**
   - Global overview endpoint: `< 200ms` (p95).
   - Single organization drill-down: `< 150ms` (p95).
   - Filtered queries with multi-campus constraints: `< 300ms` (p95).

## 7. Migration & Data Seeding Strategy

When Phase E-09.9 backend models are provisioned:
1. Seed default national and international grading scale templates.
2. Provide default 3-term and 2-semester academic calendar presets during tenant onboarding.
3. Establish data validation triggers rejecting invalid date sequences (`start_date >= end_date`).
4. Execute backfill migrations linking existing student admissions to the designated current academic session.
