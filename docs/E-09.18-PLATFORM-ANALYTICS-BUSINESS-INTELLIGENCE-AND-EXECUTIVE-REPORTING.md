# Phase E-09.18 — Platform Analytics, Business Intelligence and Executive Reporting Governance

## 1. Executive Summary & Architecture Overview

Phase **E-09.18: Platform Analytics, Business Intelligence and Executive Reporting Governance** establishes a centralized, executive-grade Business Intelligence (BI) and analytics governance workspace for the Super-Admin dashboard (`dashboard/`).

Prior to E-09.18, administrative reporting and performance visibility across the multi-tenant SaaS platform were fragmented. Individual operational screens (Tenant Management, Subscriptions, System Health, Communications, Support Desk) presented localized status lists, but platform owners lacked a unified analytical command center to inspect:
- Portfolio-wide tenant population growth and lifecycle transitions.
- Currency-isolated monetization metrics (MRR, ARR, ARPU) without coercive mixing.
- Entitlement versus actual enablement across the Master Tenant Module Registry.
- Support workloads, resolution velocity, and explainable customer-success account health.
- Platform operational reliability, capacity alerts, and backup checksum verification.
- Communication dispatch success rates and channel utilization.
- Compliance posture, security event triage, and privileged administrator audit events.
- An authoritative, documented Metric Catalog with explicit formulas, boundaries, and limitations.
- A formula-injection-safe tabular Report Generator supporting both CSV and JSON exports with audit metadata.

### Core Architecture Pillars

1. **Centralized Executive Command Center (`/analytics`)**:
   - Single-entry workspace organized into 10 tabbed domain panels:
     1. Executive Overview
     2. Tenant Growth & Lifecycle
     3. Subscriptions & Monetization
     4. Module Adoption
     5. Support & Customer Success
     6. Platform Operations
     7. Communications Analytics
     8. Audit & Governance
     9. Reports & Exports Hub
     10. Metric Catalog & Definitions
2. **Global Reporting Controls Toolbar**:
   - Synchronized, cross-cutting filter toolbar providing date range presets (`last_7_days`, `last_30_days`, `last_90_days`, `year_to_date`, `all_time`), custom date inputs, organization filtering, plan filtering, lifecycle status filtering, module filtering, and reporting currency selection.
3. **Telemetry & Data Freshness Honesty**:
   - Explicit categorization of all data sources as `verified_repo`, `simulated_fixture`, `static_config`, `not_connected`, or `unknown_stale`.
   - Missing data is never coerced to zero.
   - Non-existent telemetry is explicitly labeled as simulated or unavailable.
4. **Zero-PII & Privacy-First Reporting**:
   - Strictly aggregates organizational and operational telemetry.
   - Zero student, parent, or teacher personal identifiable information (PII) is exposed in cards, charts, tables, or export downloads.
5. **Formula-Injection-Safe Tabular Exporter**:
   - Escapes dangerous spreadsheet formula triggers (`=`, `+`, `-`, `@`, `\t`, `\r`) with single-quote neutralization.
   - Embeds reporting date range, execution timestamp, and demo disclosure metadata headers.

## 3. Global Reporting Controls & Date Interpretation Semantics

### 3.1 Date Boundary Contract

All analytics filters and time-series evaluations adhere to a single, unambiguous date interpretation standard:

```typescript
export interface ReportingDateRange {
  preset: DatePresetKey;
  startDate: string; // ISO 8601 YYYY-MM-DD
  endDate: string;   // ISO 8601 YYYY-MM-DD
  label: string;
}
```

- **Inclusive Boundary Normalization**:
  - Start boundary: `YYYY-MM-DD` expands to `T00:00:00.000Z` (inclusive).
  - End boundary: `YYYY-MM-DD` expands to `T23:59:59.999Z` (inclusive).
- **Timezone Invariance**:
  - All comparisons parse ISO strings into UTC millisecond integers (`getTime()`).
  - Off-by-one errors are eliminated by explicitly parsing UTC midnight rather than relying on local machine timezone offsets.
- **Custom Range Inversion Protection**:
  - If a user inputs a `startDate` that falls after `endDate`, `resolveDateRange()` automatically normalizes by swapping the boundaries (`[min(s, e), max(s, e)]`).
- **Deterministic Evaluation Anchor**:
  - When evaluating relative presets (`last_7_days`, `last_30_days`, `last_90_days`), the evaluation uses `ANALYTICS_REFERENCE_DATE` (`2026-10-21T00:00:00.000Z`) as the deterministic anchor point, ensuring reproducible metrics and resilient automated testing.

## 4. Domain Metric Calculation Engine & Formulas

All metric calculations are isolated in `dashboard/lib/analytics/evaluator.ts` and verified in `dashboard/tests/platform-analytics.test.ts`.

### 4.1 Executive Overview Metrics

| Metric ID | Display Name | Mathematical Formula / Aggregation Logic | Data Status |
| :--- | :--- | :--- | :--- |
| `exec_total_orgs` | Total Registered Organizations | `count(organizations)` | Verified Local Store |
| `exec_active_orgs` | Active Organizations | `count(organizations where status == 'active')` | Verified Local Store |
| `exec_new_orgs_period` | New Registrations in Period | `count(organizations where createdAt in [startDate, endDate])` | Verified Local Store |
| `exec_suspended_orgs` | Suspended Organizations | `count(organizations where status == 'suspended')` | Verified Local Store |
| `exec_estimated_mrr_usd` | Estimated MRR (USD) | `sum(plan.priceMonthly)` for active USD subscriptions, normalized from annual (`priceAnnual / 12`) | Verified Synthetic Store |
| `exec_estimated_arr_usd` | Estimated ARR (USD) | `estimated_mrr_usd * 12` | Verified Synthetic Store |
| `exec_module_adoption` | Module Adoption Rate | `mean(module.totalAdoptionRatePercent)` across all master modules | Verified Calculation |
| `exec_open_tickets` | Open Support Tickets | `count(tickets where status not in ('resolved', 'closed'))` | Verified Local Store |
| `exec_sla_compliance` | SLA Compliance Rate | `(ticketsWithinTarget / evaluatedTickets) * 100` | Verified Local Store |
| `exec_operational_ratio` | Operational Service Ratio | `(operationalComponents / totalComponents) * 100` | Simulated Telemetry |

### 4.2 Monetization & Financial Metrics Safeguards

In strict compliance with SaaS BI standards:
1. **Currency Isolation**: Currencies (`USD`, `GBP`, `CAD`, `EUR`) are never summed together. Each currency maintains an independent MRR, ARR, and ARPU calculation bucket.
2. **No Coercive Multiplication**: Subscription tier prices are only counted toward MRR if an active or past-due subscription actually exists for that organization.
3. **Receivables Aging**: Unpaid and past-due invoices are grouped into standard aging buckets (`0-30 days`, `31-60 days`, `61-90 days`, `90+ days`) using explicit due-date differences.
4. **Synthetic Data Disclosure**: Financial metrics are derived from store subscription fixtures and clearly badged as simulated.

### 4.3 Support Desk & Customer Success SLA Metrics

- **First Response Time**: Calculated strictly for tickets created within the reporting window that have recorded a valid `firstResponseAt` timestamp.
- **Resolution Time**: Calculated as `diffInMinutes(resolvedAt, createdAt)` exclusively for resolved tickets with both timestamps. Unresolved tickets are strictly excluded from resolution-time averages.
- **Explainable Health Scoring**: Evaluates tenant accounts based on the E-09.17 deduction formula:
  $$\text{Score} = \max(0, 100 - (\text{openTickets} \times 5) - (\text{slaBreaches} \times 15) - (\text{isPastDue} ? 25 : 0) - (\text{configBlockers} \times 10))$$

### 4.4 Communications & Observability Metrics

- **Delivery Success Rate**:
  $$\text{SuccessRate} = \frac{\text{deliveredCount}}{\text{deliveredCount} + \text{failedCount} + \text{sentCount}} \times 100$$
  *Queued, suppressed, and draft messages are explicitly excluded from the denominator.*
- **System Health Status**: Derived hierarchically from registered operational components:
  - If any component is in `critical` or `outage`: Overall status is `critical`.
  - Else if any component is `degraded`: Overall status is `degraded`.
  - Else if any component is in `maintenance`: Overall status is `maintenance`.
  - Else: Overall status is `healthy`.

## 7. Tabular Reports & Exports Hub

The Reports & Exports Hub (`dashboard/components/analytics/ReportsExportsWorkspace.tsx`) enables authorized administrators to generate, review, and export tabular datasets.

### 7.1 Canonical Report Templates

1. `executive_overview_summary`: Cross-domain executive KPI scorecards and status totals.
2. `tenant_growth_lifecycle`: Organization inventory, campus counts, lifecycle statuses, and registration dates.
3. `monetization_ledger`: Subscription records, plan tiers, billing cycles, currency, MRR, and renewal dates.
4. `module_adoption_register`: Master module enablement counts, eligibility rates, and adoption ranking.
5. `support_operations_sla`: Ticket register, priority, SLA status, resolution times, and assignment.
6. `platform_operations_health`: Component telemetry, current health status, latency, and uptime ratios.
7. `communications_delivery`: Notification dispatches, delivery statuses, channels, and recipient identifiers.
8. `audit_governance_log`: Security events, compliance control statuses, and administrative audit trails.

### 7.2 Formula Injection Protection (`escapeCsvFormulaInjection`)

To protect administrators opening exported CSVs in Microsoft Excel or Google Sheets, all exported cell values are processed through `escapeCsvFormulaInjection()`:
- Detects leading formula trigger characters: `=`, `+`, `-`, `@`, `\t`, `\r`.
- Prepends a single quote (`'`) to neutralize automatic formula execution.
- Properly quotes text containing commas, quotes, and newlines.

### 7.3 Export Metadata Header

Every generated CSV and JSON export includes structured audit headers:
- Report title and template key.
- Generation timestamp (ISO 8601).
- Applied filter parameters (organization, plan, status, date range).
- Demo fixture disclosure notice.

## 10. Known Limitations & Future Work

1. **Client-Side Aggregation Scale**:
   - Currently, metrics are computed client-side over memory fixtures. When tenant populations exceed 10,000 organizations, aggregations must migrate to backend SQL rollups and OLAP data pipelines.
2. **Local Saved Reports**:
   - Saved report configurations are persisted in component state / local demo state. Cross-device sharing requires future backend persistence.
3. **Historical Status Reconstruction**:
   - Historical tenant lifecycle trends are derived from registration dates and current statuses. Full historical state transition analytics will require backend event-sourcing or SCD Type 2 tables.
