## 1. Executive Architecture & Persistence Strategy

To transition from deterministic client-side memory fixtures to high-performance platform data governance, the backend architecture must establish dedicated relational tables with strict referential integrity, row-level security (RLS), and append-only audit protections.

### 1.1 Relational Schema Blueprint (PostgreSQL 16+)

#### Data Category Catalog (`governance_data_categories`)

```sql
CREATE TABLE governance_data_categories (
    id VARCHAR(64) PRIMARY KEY,
    code VARCHAR(32) NOT NULL UNIQUE,
    name VARCHAR(128) NOT NULL,
    description TEXT NOT NULL,
    data_subject_type VARCHAR(32) NOT NULL CHECK (data_subject_type IN (
        'student', 'guardian', 'staff', 'organization', 'system', 'applicant', 'vendor'

    classification_level VARCHAR(32) NOT NULL CHECK (classification_level IN (
        'public', 'internal', 'confidential', 'restricted'

    retention_policy_id VARCHAR(64) REFERENCES governance_retention_policies(id) ON DELETE SET NULL,
    lifecycle_status VARCHAR(32) NOT NULL DEFAULT 'active' CHECK (lifecycle_status IN (
        'active', 'restricted', 'archived', 'scheduled_deletion'
    )),
    review_status VARCHAR(32) NOT NULL DEFAULT 'current' CHECK (review_status IN (
        'current', 'needs_review', 'under_review'
    )),
    sensitive_attributes TEXT[] NOT NULL DEFAULT '{}',
    applicable_regulations TEXT[] NOT NULL DEFAULT '{}',
    notes TEXT,
    last_reviewed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
```

## 2. Distributed Lifecycle Orchestration (Temporal / BullMQ)

In a live production environment, retention policies and lifecycle rules cannot rely on synchronous web request handlers. They must run via distributed workflow orchestrators (e.g., Temporal or BullMQ).

### 2.1 Daily Retention Evaluation Workflow

```text
[Cron: Daily 02:00 UTC]
        │
        ▼
[Fetch Active Retention Policies & Lifecycle Rules]
        │
        ▼
[Query Candidate Records Past Retention Horizon]
        │
        ▼
[Check Active Legal Holds (governance_exceptions)]
        ├── If Active Legal Hold Exists ──> [Bypass Deletion & Tag as RETAINED_EXCEPTION]
        │
        └── If Clean (No Holds)
                │
                ├── If Archive Rule: [Transition to S3 Glacier Deep Archive]
                │
                └── If Purge Rule:
                        │
                        ├── [Generate Anonymization Tombstone Receipt]
                        ├── [Cryptographic Shredding of Tenant Key or Overwrite]
                        └── [Write WORM Audit Ledger Record]
```

### 2.2 Dual-Authorization Interceptors

- High-impact lifecycle actions (e.g., executing tenant-wide erasure or updating permanent record retention policies) require dual administrative authorization.
- The workflow pauses in a `pending_secondary_approval` state until a second administrator with the `super_admin_dual_key` role signs the cryptographic token.

## 3. Cryptographic Storage & Envelope Key Management

Data classified as **Restricted** (cumulative academic transcripts, child welfare/safeguarding notes, medical directives) requires envelope encryption via AWS KMS or HashiCorp Vault.

### 3.1 Envelope Encryption Scheme

1. **Master Key (KEK)**: Stored in hardware security modules (HSM) managed by AWS KMS / Cloud KMS with annual automated rotation.
2. **Tenant Data Encryption Key (DEK)**: Generated per tenant or per restricted data subject using AES-256-GCM.
3. **Cryptographic Shredding on Erasure**: When a legitimate Right-to-be-Forgotten request is executed for non-statutory records, the backend shreds the specific DEK, rendering all corresponding encrypted ciphertexts permanently unrecoverable across all database snapshots and backups without needing physical database vacuuming.

## 4. DSAR Identity Verification & MFA Handshake Webhooks

Production DSAR workflows must never disclose pupil records based solely on unauthenticated web form submissions:

1. **Parent/Guardian Identity Challenge**:
   - The platform sends a time-limited (15-minute) cryptographic magic token via verified SMS/email.
   - For student records, the backend verifies that the requesting party matches the legal custody records in `cat_parent_guardian`.
2. **Third-Party Regulatory Verification**:
   - Official information commissioner inquiries require manual verification of the investigator's government credentials by Platform Legal Counsel before advancing the state machine to `under_review`.

## 5. Legal Hold Interceptor Middleware

To guarantee that retention rules and purge jobs never delete evidence subject to ongoing litigation or statutory tax inspection:

```typescript
// Proposed Database ORM Interceptor / Prisma Middleware
async function legalHoldGuardMiddleware(params, next) {
  if (['delete', 'deleteMany', 'update', 'updateMany'].includes(params.action)) {
    const { model, args } = params;
    
    // Check if the entity is subject to an active legal hold
    const activeHolds = await db.governanceExceptions.findMany({
      where: {
        reviewStatus: 'approved_demo',
        expirationAt: { gt: new Date() },
        OR: [
          { tenantId: 'platform_wide' },
          { tenantId: args.where?.tenantId }
        ]
      }
    });

    if (activeHolds.length > 0) {
      const conflictingHold = activeHolds.find(h => 
        h.relatedCategoryId === modelToCategoryMap[model]
      );
      if (conflictingHold) {
        throw new LegalHoldEnforcementError(
          `Operation blocked: Entity "${model}" is locked under Legal Hold ${conflictingHold.code}: ${conflictingHold.title}`
        );
      }
    }
  }
  return next(params);
}
```
